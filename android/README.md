# Music Android — native alpha

An experimental Kotlin/Jetpack Compose client, not a WebView wrapper. Application ID: `com.everyonesoftware.audio`; version `0.1.<Git commit count>`; minimum Android API 26; compile/target API 36. Before the first commit, local debug builds use `0.1.0`. The current UI follows the readable, playlist-first v5 draft. Its colors are provisional.

Music replaces Audio as the native app's display name only. The application ID, signing key/configuration, and local data identifiers remain unchanged to support updates to existing installs without resetting saved accounts or listening sessions. Historical browser mockups retain their original names; this rename is not a claim of device verification.

## Current slice

- Native GitHub-backed updates: daily foreground checks, manual checking, Library/Now Playing download-dot icons, explicit download/cancel/retry, package/version/signer/integrity preflight and a user-confirmed Android installer flow. The offered manifest supplies precomputed, locally prepared What’s new groups and original Commit details; opening disclosures never requests history. Checking/downloading never sends a playback command; installation requires paused playback and a saved-session checkpoint. See [UPDATING.md](UPDATING.md) for privacy, signing, permission and verification boundaries.
- Welcome → connect with an existing Navidrome username/password → accessible libraries → playlists → full player.
- Direct Subsonic-compatible requests to the configured server, including base paths. No Music account/backend/proxy.
- Playlist search and a direct Shuffle action. Refresh puts the most recently played playlist first. The car browser opens collection contents with Play and Shuffle play action items; this is not a longer recent-playlist history.
- Playlist browsing shows cached rows immediately, then reconciles counts from actual `getPlaylist` entries with at most three detail requests at a time. A list-summary count of zero never disables Shuffle; an empty result is checked when starting playback. Refreshing counts does not replace or edit the listening queue.
- Entering Playlists, returning to the foreground on that screen, and the persistent Refresh action request reconciliation. Successful rating changes invalidate counts and schedule debounced retries: six seconds by default, or after the affected playlist's advertised OpenSubsonic `validUntil` deadline when later. Different validity deadlines do not delay other playlists. Servers that omit this metadata and use a longer custom delay may still require a later manual refresh. Unavailable counts retain their last known values and are labelled instead of silently becoming zero. There is no continuous polling or forced server reevaluation.
- Media3/ExoPlayer owned by `PlaybackService`, with a media session, audio-focus handling and audio-becoming-noisy handling. UI controllers do not own or duplicate players.
- Adaptive launcher and round icons fill the phone's icon mask without a square tile/white corners. Android 13+ themed icons have a monochrome layer. The media notification and car media-card attribution use a transparent monochrome equalizer.
- A persisted queue contains every playlist occurrence, its exact order, connection, playlist, current index, last committed position, repeat mode, shuffle flag and queue identity. A fresh Shuffle creates a new queue identity even if its track order happens to match the previous one.
- A cold launch restores the full player **paused**. Reopening while the service is already playing reconnects without stopping it. Progress is checkpointed approximately every second and on transport/lifecycle events; an abrupt kill can lose an uncommitted checkpoint, not generate a new shuffle.
- Shuffle-on reshuffles the visible queue around the current song. Shuffle-off retains the existing visible order; this alpha does not reconstruct the playlist's original unshuffled order.
- The title-side rating trigger opens five large choices. `setRating` is followed by `getSong`; only the server-confirmed value becomes local state. Failures retain the last confirmed value. Clear sends zero. Responses are bound to the captured account/song, not whichever song is visible when a request completes.
- Settings supports adding/switching connections, changing accessible-library selections and opening Navidrome administration in the browser. Library preferences are local browsing preferences, not permissions, server folder management, playlist filters or changes to an existing queue. Local account removal UI and playlist editing are not implemented.

## Phone Artists

Library includes Artists after Playlists and Albums, an all-artists list with its own query, and artist matches in global Search. The ID3-tag index comes from `getArtists`; opening an artist reads `getArtist` and then every listed `getAlbum` in server order. Only a completely successful aggregate publishes album/song counts or enables playback. Failed or truncated albums fail the whole artist load; repeated song occurrences are retained. Refresh/retry is account-scoped, and account switches cancel/reset artist requests, selection and queries.

Artist details use native circular artwork (or a native person placeholder), a centered name/count summary, and centered icon-only **Play → Shuffle** controls. Play starts a fresh ordered queue; each Shuffle immediately starts a fresh shuffled whole-artist queue. Albums and All songs share the fully loaded snapshot. Selecting a song starts the complete ordered artist queue at that occurrence, including earlier tracks for Previous. Album Back returns to the artist; artist Back returns to the original Library, Search or all-artists page. There is no artist download action or saved-playlist creation. Offline artist browsing/playback is explicitly unavailable; existing downloaded album/song playback remains under Saved music.

The source type `artist` uses the existing persisted listening session and PlaybackService/Media3 controller. Controller availability, captured account/detail ownership and previous queue identity are checked before replacement. Android Auto's root remains **Playlists / Albums / Queue**; artist expansion and voice artist resolution are not included.

Focused native verification, after installing both APKs on an explicitly owned emulator:

```sh
adb -s <owned-serial> shell am instrument -w -r -e class 'com.everyonesoftware.audio.ArtistFlowTest,com.everyonesoftware.audio.ui.ArtistViewModelTest,com.everyonesoftware.audio.ui.AudioScreensTest#artistHeaderCentersNeutralImmediatePlayThenShuffleAtCompactAndPhoneWidths,com.everyonesoftware.audio.ui.AudioScreensTest#artistCountsAndActionsWaitForFullLoadAndErrorRetryIsExplicit' com.everyonesoftware.audio.test/androidx.test.runner.AndroidJUnitRunner
```

Require `OK (6 tests)`, six successful test-completion statuses, and no failure/crash/assumption-skip statuses. `ArtistFlowTest` exercises the actual activity, account-scoped HTTP/audio fixtures, duplicate-containing complete artist queues, repeated ordered/shuffled Play, album/origin Back, native service timelines and persisted queue readback. View-model fixtures cover gated later-album failure/retry, controller unavailability, offline rejection, empty catalog reentry and a delayed old-account response. UI fixtures check compact 320dp and normal 412dp centered geometry, neutral immediate actions, unknown counts and unavailable states. These fixtures do not establish physical-device audio, a personal Navidrome deployment or Android Auto artist browsing.

## Collection song selection and Played queue

Phone playlist/album song taps capture the displayed collection, account, ordered occurrences and selected occurrence index. They create a fresh whole-collection queue with shuffle off, rather than singleton/tail playback. Loading, failed, offline, account-changed or stale detail selections are rejected; the controller is acquired before replacing the saved session. Saved-collection offline transport remains a separate completeness-checked path.

Queue has a collapsed **Played** disclosure, a separate **Now playing** row and **Up next**, with real per-song artwork and no track numbers. Played is not the prefix before the selected index: selecting occurrence three starts with no visits. Only the shared playback service's `Player.isPlaying` evidence marks a visit started; leaving that visit, repeating it, or reaching the end records it. Failed/unstarted selections, paused restoration and skipped occurrences do not invent history. Replay/native queue selection preserves queue identity. Stable occurrence tokens retain duplicate identity across in-session shuffle; repeated visits remain separate history entries. The latest 1,000 left/finished visits are persisted per listening session, with backward-compatible empty history for old saved data. The current visit's started flag is deliberately not restored as evidence after process death.

Android Auto renders the existing native root and collections itself. Its Queue contains **Played** (browsable), the current playable song labelled **Now playing**, and **Up next** (browsable). History/current/upcoming songs share service-owned evidence and account-scoped opaque artwork capabilities; no custom car screen is introduced. Phone actions, voice and native/legacy controllers use the same player listener. New history/service/UI regression fixtures compile into the instrumentation APK; compilation alone does not establish device execution or head-unit rendering.

Installer progress is fenced by captured occurrence order as well as account,
queue and song IDs. After the save await, installation rechecks the paused
controller identity, selected media occurrence and current session order before
emitting the install request. Reordering identical duplicate songs must neither
accept an old numeric-index checkpoint nor hand off a stale installation.

After the unit-test build has populated the Gradle dependency cache, run
`node --test android/validation/install-update.test.mjs` from the repository root
with JDK 21 (`JAVA_HOME`) and the same `GRADLE_USER_HOME` as the build. This harness
compiles the **actual** `installUpdate` and mutex-protected `updateProgress` method
bodies with real session/occurrence rules and controlled Android/controller,
updater and storage boundaries. Its `progress`, `handoff`, `controller`, and
`resume` cases failed RED before the fix; all five cases including `success` are
GREEN. This is executable JVM integration-boundary coverage, not native installer,
Room, service or activity acceptance.

## Phone media output

Now Playing shows the current Android media output at bottom left and Queue at bottom right. Tapping the output opens a native device picker. On Android 14+ it requests Nearby devices access (`BLUETOOTH_CONNECT` and `BLUETOOTH_SCAN`) and lists only system routes actually reported by Android. It does not scan for unpaired devices, offer Cast destinations, or invent separate speaker/wired outputs when Android exposes only a combined device route.

Output changes use `MediaRouter2.transferTo`; the displayed selection changes only after Android confirms it. Pending transfers, disconnects, rejected requests and timeouts stay separate from the listening queue. Routing observers run only while the activity is in the foreground and refresh when it resumes or permissions change. Pairing remains in Android device settings.

On Android 8–13, the picker reports the current framework route and links to Android device settings rather than claiming to switch devices using legacy route bookkeeping, which can disagree with hardware while playback is paused. No privileged audio-routing permission, call-audio override or ExoPlayer preferred-device hint is used.

Validation separates real framework route reporting/permission updates on an emulator from deterministic transfer tests using an injected backend. Audible Bluetooth/wired transfers, paused-device behavior and physical disconnects still need a hardware trial.

## Android Auto: first integration, not yet host-validated

The manifest declares media support, and the existing `MediaLibraryService` serves **Playlists / Albums / Queue**, in that order. Android Auto supplies the actual browsing and playback UI; this is not a custom car activity or the HTML mockup embedded in a WebView.

- Playlist and album catalog rows are **browsable, not playable**, with no custom Play/Shuffle supported commands or advertised media-item command buttons. Opening a collection awaits its contents without changing playback. Contents starts with two ordinary playable **Play**, then **Shuffle play** action items, followed by every ordered song occurrence. Each action creates a fresh complete ordered or shuffled queue at the beginning. Choosing a song starts the complete ordered collection at that exact occurrence, retaining earlier songs for Previous. Duplicate songs have distinct occurrence IDs. Empty collections cannot start playback; missing/failed collections return safe errors rather than replacing the current queue.
- List-style hints request list rendering for contents/action items. Collection metadata supplies the actual playlist/album title, song count and real collection artwork when available. Android Auto owns the contents header, artwork placement, action presentation, Back and Now Playing controls. Native media browsing cannot reproduce the illustrative HTML's top-right pills or dictate pixel placement; no car Activity, WebView or mockup SVG/sample art is shipped. Exact host placement/navigation still needs DHU or vehicle validation.
- Canonical IDs are connection-scoped: playlist `play` / `shuffle` / occurrence-indexed `track`, and album `albumplay` / `albumshuffle` / occurrence-indexed `albumtrack`. Song selection validates the current collection, index and song identity; foreign-account, malformed and stale occurrence IDs are rejected. Existing playlist collection, shuffle/song and voice IDs remain accepted. Compatibility command handlers for `com.everyonesoftware.audio.PLAY_COLLECTION`, `com.everyonesoftware.audio.SHUFFLE_COLLECTION` and playlist-only `SHUFFLE_PLAYLIST` remain available with Media3's `EXTRA_KEY_MEDIA_ID`, but are not advertised as row buttons.
- In offline mode both catalogs and contents metadata come only from account-scoped saved collection snapshots, without API refreshes. A partially downloaded snapshot can still show its complete song list. Play, Shuffle play, individual-song selection and voice playback all require every saved song to be complete; none filters out missing songs. Play keeps saved order; Shuffle play shuffles every occurrence. Album selections use the album playback source.
- The current playlist sorts first; this is separate from the session's actual Played visits. Car and phone share one player and one persisted queue. Queue occurrence IDs include the connection, queue identity, and stable occurrence token, so duplicate songs remain distinct through shuffle and stale queue selections cannot target a replacement queue.
- Browser subscriptions receive queue-change notifications after a phone selection. Library/network failures return safe errors; reloading the requested list retries the request without replacing the listening session.
- Car browse/search waits only for playlist summaries, with a short summary freshness window, while count reconciliation runs separately. Playback fetches only the selected contents; a slow or failing unrelated playlist cannot block selection. Playlist subscribers are notified when completed reconciliation changes displayed names/counts, including rating-triggered refreshes from the phone. Count snapshots are persisted in batches with serialization off the main thread, and protocol requests reuse an account-scoped client.
- Voice search matches playlist names: a unique exact name wins, otherwise a unique partial match is required. Ambiguous or missing matches fail without picking arbitrary music. An empty playback query resumes an existing session. Artist, album, and song search are not implemented. The native voice intent is handled on first creation or a new intent, not replayed on recreation.
- Cold browser connection restores the stored queue/index/position/repeat state paused. An explicit playback command resumes it; merely browsing never autoplays or reshuffles. This is a local controller contract, not a claim about the host's own launch/autoplay policy.
- Music controls advertise previous/next-track actions, not ten-second rewind/fast-forward. In-track seeking remains available for the phone slider. Legacy previous restarts the current song after the player's normal threshold; near the beginning it selects the previous occurrence. Both Media3 and platform-legacy tests exercise actual track changes and preserve the saved queue.
- Server/account setup and five-star ratings stay on the phone. Current-song artwork has two media-session representations: a small embedded JPEG (up to 256 pixels / 128 KiB) for bitmap consumers, and an opaque local `content://` URI serving a higher-quality JPEG (up to 1024 pixels / 1 MiB) for car hosts and other URI consumers. The host chooses its representation; the app does not force every consumer to use the small thumbnail. Phone artwork is unchanged and small source images are not upscaled.
- Both current-song versions share one authenticated `getCoverArt` download requesting size 1024. Downloads are capped at 2 MiB and ten seconds, get one retry, and never block or fail music playback. A four-cover credential-scoped memory-only LRU retains both versions together. Only the current queue occurrence retains embedded image bytes; every covered song retains an opaque browse artwork URI. Track/queue/account changes cancel obsolete work and reject late results. The current-song full-image URI is published when ready, with no network request on a current-song provider read.
- Collection artwork uses separate graph-owned, authenticated encrypted `content://` capabilities: no credentials, server URL, plaintext cover ID or private file path enter metadata. An account/process-scoped memory-only AES-GCM key validates the tokens; a 256-entry LRU only reuses recent tokens, so eviction does not invalidate artwork already returned to a host. Catalogs and search results apply pagination before creating artwork metadata; counting search results creates no artwork tokens. Legacy unpaged catalogs retain valid artwork without an unbounded registry. Listing metadata does not fetch/decode every cover or embed bitmap payloads in Binder results, and never replaces the current-song artwork owner. The same trusted read-only provider resolves actual cover bytes through `ArtworkCache.load` on its pipe worker, checking account ownership before and after loading. It uses retained local bytes offline and never attempts offline API access. Account changes/removal, explicit clearing and process death revoke future collection reads; unavailable artwork leaves a host placeholder. A car-player shuffle toggle remains deferred.

Automated verification uses isolated fixtures, not a personal account or physical vehicle. The user reports working Android Auto vehicle playback and Tesla Bluetooth playback, with intermittently absent Tesla artwork in the earlier build. The new contents/artwork presentation still needs a vehicle retest. Host/DHU checks for controller trust, contents/action placement, day/night presentation, interruptions and reconnect behavior remain distinct from browser callback tests and host certification or Play distribution review.

Implementation follows the pinned Media3 1.8.0 APIs. References: [Serve content](https://developer.android.com/media/media3/session/serve-content), [Android for Cars media](https://developer.android.com/media/implement/surfaces/cars), [car artwork through local URIs](https://developer.android.com/training/cars/media/create-media-browser/media-artwork), and the [1.8.0 session source](https://github.com/androidx/media/tree/1.8.0/libraries/session/src/main/java/androidx/media3/session).

### Personal sideload / vehicle trial

Android Auto can show generic media controls for phone playback without recognizing Music as a browsable car app. A generic media card or an "opened on phone" message does not by itself identify the cause. This build already exports a native media browser with Playlists, Albums and Queue; it does not need to display the phone activity to browse or play music.

For a GitHub/manual APK install, check Android Auto's **own** developer setting, **Unknown sources**. Google's [real-vehicle testing guide](https://developer.android.com/training/cars/testing#unknown-sources) documents this opt-in for sideloaded media apps; signing an APK alone does not make its installation source trusted. This setting is distinct from Android's permission to install APKs:

1. While parked, open Android Auto settings on the phone, expand the Version information near the bottom, and tap the version/permission information ten times. Accept the development-settings prompt.
2. Open the overflow menu → Developer settings → Unknown sources. This allows other sideloaded compatible media apps too; enable it only if you accept that broader scope.
3. Reconnect Android Auto and check whether Music is available in its launcher/customize-launcher list. Open **Music**, not the generic fallback media shortcut, and verify Playlists / Albums / Queue browsing, the separate Play and Shuffle play actions, queue occurrence selection and previous/next controls.

If Music still opens only on the phone, collect the installed Music version, Android Auto version and service connection logs before changing controller authorization. Do not bypass UID/trust checks or pretend to be installed by Google Play. A trusted Play testing distribution is an alternative to the developer opt-in. Actual host rendering/recognition still requires a DHU or vehicle retest after updating the APK.

## Build

Prerequisites: **JDK 21**, Android SDK platform 36 and build tools 36.0.0. Point `JAVA_HOME` at JDK 21. In Android Studio, select JDK 21 for Gradle; an existing bundled Java 25 is not a compatible substitute for this pinned Gradle 8.13 build.

Open this `android/` directory in Android Studio. Set `ANDROID_HOME` to the local SDK, or create an ignored `local.properties` containing `sdk.dir=<local SDK path>`. No SDK paths, signing keys or credentials belong in Git.

From `android/`:

```sh
./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug :app:assembleDebugAndroidTest
```

On Windows cmd/PowerShell use `gradlew.bat` instead of `./gradlew`. The wrapper pins the Gradle distribution SHA-256. The APK is `app/build/outputs/apk/debug/app-debug.apk` and uses a local **debug** signing key. Signed release builds and GitHub publication are configured separately in [RELEASING.md](RELEASING.md); persistent signing secrets are required. The [in-app updater](UPDATING.md) checks automatically but downloads and installation require user approval; debug and release signers are not interchangeable.

Use an explicitly chosen, task-owned emulator, not a personal device. After building both APKs:

```sh
python ../scripts/test-android-device.py --serial emulator-5580
```

Set `ANDROID_HOME` or pass `--adb <adb executable>`. An optional `--class <fully qualified class or class#method>` filters tests. The runner refuses non-emulator serials, installs the two APKs, and requires an actual JUnit `OK` summary: `am instrument` can exit zero even when assertions fail. Results are saved under the root's ignored `test-results/`.

Verified on an isolated API 36 Google APIs x86_64 emulator:

- Android lint passes with **zero errors** and warnings (mostly available dependency/target updates, the intentional exported media service and a KTX style suggestion). No baseline or lint-error suppression was used to turn failures green.

## Security boundaries

- Production credentials start blank. The mockups' prefilled dummy forms do not enter the Android app.
- Release URLs require HTTPS; debug permits HTTP only for `localhost`, `127.0.0.1` and the emulator's `10.0.2.2` host bridge. Ordinary LAN HTTP and certificate-validation bypasses are not supported.
- Passwords are AES-256/GCM encrypted with a per-installation Android Keystore key; connection identity is authenticated as associated data. Passwords and token-bearing URLs are not stored in UI state, playback metadata or session JSON. Room's library/session metadata is app-private, not whole-database encrypted.
- Cloud backup/device transfer of account and listening data is excluded. Keystore/ciphertext failures fail closed and require reconnecting.
- API and media redirects are disabled. Media items hold unsigned stream references. The service captures credentials per queue and authenticates immediately before a request; stale queue/account requests are rejected. Playback errors do not expose credential-bearing causes.
- Phone artwork uses an uncached image loader with redirects disabled. URLs are remembered per artwork/connection rather than regenerated on every progress tick. Session artwork uses a separate bounded authenticated download and memory-only dual-image cache; no disk cache, signed URL, or transport exception is published. The exported read-only artwork provider admits only the app's UID or callers trusted for media control, resolving actual Binder identity through PackageManager. Random local URIs contain no server/account/cover IDs. Reads recheck active credentials; eviction, account changes, service shutdown and process death invalidate future reads (already-open pipes cannot be revoked). The provider exposes current-song cached bytes or registered collection covers loaded on a pipe worker through the account-scoped artwork cache, never arbitrary network URLs or filesystem paths. Collection capabilities use a separate bounded registry and are revoked on account changes without clearing current-song artwork. System media consumers can receive cover images just as they receive the current song's title and artist. Very large, malformed or unavailable covers fall back to host placeholders without interrupting audio.
- The media service is exported for OS media-session integration, but `onConnect` admits only the app's own UID/package or controllers trusted by Android. Legacy binding initially uses a synthetic unknown-UID lookup; returning a session for that lookup is not authorization of the real caller. Set-item requests resolve only canonical app IDs or bounded playlist-name searches; controller URIs and arbitrary add/remove/reorder operations are rejected. Stream references and credentials are reconstructed by the service, not supplied by the controller.
- Session mutations are serialized. Progress writes are checked against the connection, queue identity and exact song sequence **inside** the state lock, preventing a late old tick from overwriting a new shuffle.
- Asynchronous car selections also check their captured credentials and prior queue under that lock. A late response cannot replace a newer phone queue or a different account. Selecting an existing queue occurrence preserves concurrently confirmed rating/repeat metadata.

## Explicit limits / next verification

This is a first native slice, not a production release. No personal server, real credentials or physical phone were used. Real Navidrome deployments, reverse proxies, unusual libraries, API-key-only authentication, hardware codecs, Bluetooth/headset controls, real lock-screen behavior, interruptions, battery restrictions and older Android versions need further verification. The current authentication UI supports username/password token authentication, not API-key-only accounts.

Offline music downloads, casting, equalization and playlist editing are not implemented. The Android Auto integration described above still needs real host/DHU and vehicle testing. The GitHub release workflow supports signing/publication once repository secrets are configured; hosted publication is verified separately from local builds. Server administration remains in Navidrome. App updates are user-confirmed, not silent or forced.

For a first personal trial, install the debug APK manually and enter credentials **in the app**, not in chat or repository files. Use a valid HTTPS address, including any reverse-proxy base path. Never disable TLS validation to work around a certificate problem.
