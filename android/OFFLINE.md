# Android storage and offline playback

- Played audio and full-song fetches share one app-private Media3 span store under `files/offline-music`; the HTTP client remains `cache(null)` / `no-store`. These are intentionally separate layers.
- Automatic saving defaults to on, with a 2,000,000,000-byte budget. The selected/current track is fetched first, then the next track, at most three recent interrupted saves, then the remaining configured upcoming tracks. Only interrupted entries with actual retained spans are retried; evicted zero-byte metadata is not a download request.
- Upcoming tracks and interrupted recovery require an unmetered connection unless mobile prefetch is enabled. The current track uses the connection used for playback. Explicit downloads are user-initiated and may use metered data.
- Completeness requires both Media3 coverage of every byte and matching lengths of the actual span files. Truncated/missing spans are invalidated and availability is republished. Partial audio is never shown as offline-ready. Offline mode rejects an incomplete song before exposing its partial bytes. Recency writes are best effort: unwritable metadata does not prevent reading intact saved audio.
- Foreground playback reads the shared cache without taking writer holes. A separate priority worker fills the entire current song, so completion does not wait for playback to consume it. An initial cache miss may issue parallel playback/fetch HTTP requests; this is not transport deduplication. Subsequent replay and seeking reuse stored bytes. Data sources support repeated open/close cycles and serialize delegate access against cancellation.
- Prefetch wraps at the end of repeat-all queues; repeat-one does not prefetch unrelated queue songs. Turning upcoming prefetch off still permits bounded interrupted-played-song recovery on an allowed connection.
- Keys hash length-prefixed connection ID, server, account, song and representation fields, never signed URLs. Account/generation checks surround every source open and read, including cache hits. Account removal tombstones keys, closes sources and removes metadata and spans; late commits are removed by the span listener.
- A shared network policy rejects new music-server calls and cancels in-flight API, artwork and streaming calls when offline mode is enabled. Existing playback sources are closed and the service prepares the same index/position again without changing the latest play/pause intent.
- Whole-song fetch failures retry at a bounded interval and on connectivity changes. Finishing an errored current song can re-prepare the player; this does not issue `play()` or override a pause.
- Automatic LRU eviction does not remove pinned downloads or the current playback target. An actively protected song may temporarily exceed the configured automatic budget. Download bytes are counted separately and are not part of the automatic budget.
- Clearing automatic audio storage resumes any interrupted explicit downloads in pinned-only mode; it does not immediately refill the automatic entries that were just cleared. Saved music returns through Settings without replacing the original browser navigation origin.
- Download actions are available for individual songs and whole albums/playlists. Collection downloads atomically persist an account/server-scoped snapshot: kind, ID, name, artist/year, cover ID and the exact ordered song list (including duplicates), alongside independent pin owners. Snapshot refresh failure leaves the previous durable/live snapshot unchanged. Clear automatic cache retains pinned audio and collection metadata; pinned work resumes on account activation.
- Settings exposes the budget presets/custom MB, upcoming count, metered opt-in, offline mode, separate usage and complete-song counts, confirmed cache clearing, and a saved-song view. Its Recently played tab is driven only by actual player events, with an Offline only filter; background fetches do not become listening history. Complete downloads can be individually removed, and pending downloads can be cancelled. An active reader remains protected when unpinned.

## Deliberate limitations

Interrupted downloads resume when the app/account is activated; there is no WorkManager/DownloadService guarantee of continued work after Android kills the process. The fixed representation key identifies the server's default stream policy; if user-selectable transcoding is added, it must introduce distinct representation keys.

## Saved collections

Settings → Saved music lists downloaded albums/playlists as well as songs. A collection opens its durable detail view without an API request. Counts include duplicate occurrences; Complete/Partial labels reflect actual complete audio. “Play in saved order” is enabled only when every song is complete. Incomplete songs remain visible and are never silently skipped. Playback uses the existing `album`/`playlist` SessionRules sources with shuffle disabled, then the existing queue-ID media-session resolution path. Offline car playlist browsing/search/resolution also uses these snapshots without refreshing the catalog or contents.

Removing/cancelling a collection releases only its `collection:<kind>:<id>` pins. Songs still owned by another collection or an explicit `song:<id>` download remain pinned. Individual removal/cancellation releases only the explicit song owner; collection-only songs direct users to their collection. The final owner removal deletes inactive audio; active foreground audio remains protected. Account removal purges snapshots and metadata, and stale-account operations are rejected. Artwork ownership is reconciled centrally from the authoritative pinned-song and collection snapshots, rather than separate view-model pin/removal writes. This includes the collection cover and every song cover; obsolete owners are dropped together. The view model returns only local ArtworkCache URIs and observes its revision for recomposition.

Verification: `OfflineCollectionsTest` exercises persistence, duplicate order, account/server isolation, shared/explicit ownership, failed refresh rollback, partial playback rejection and account purge on the JVM. `OfflineCollectionCacheTest` and `OfflineCollectionScreensTest` cover native storage ownership and UI hierarchy/actions; these require emulator execution separately from APK compilation.

## Persistent artwork

Artwork is stored below app-private `files/offline-artwork`, with hashed server/account/connection/cover keys. Only normalized bounded image bytes and unsigned ownership metadata are persisted, never authenticated URLs. Automatic artwork has a separate 50 MB LRU budget. Download-owned covers are pinned outside that budget and survive automatic clearing; shared owners release independently. Length and SHA-256 validation reject corrupt local images. Reading intact art does not require a successful recency write.

Browsing and media-session artwork use the same local-first store. UI URI resolution is memory-only; disk verification, decoding and downloading run on IO/default dispatchers and publish a revision when local artwork becomes available. Media notifications continue using the existing trusted, revocable content-provider surface, not direct private-file URIs. In-flight work is invalidated on account changes/removal, offline mode blocks remote fetches, and automatic clearing does not cancel an explicit pinned-cover download. Current media artwork can retry transient failures independently of browsing cooldowns and observes later successful cache revisions.

`ArtworkStoreTest` covers persistence/isolation, shared pins, authoritative reconciliation, integrity/size bounds, LRU and metadata-write failure. `ArtworkCacheTest` covers native decode, offline reopen/session use, main-thread StrictMode lookup, late removal, invalid images, pinned downloads during automatic clear and transient retry. `OfflineCollectionFlowTest` launches the production activity, opens saved playlist hierarchy after activity restart, plays its duplicate-preserving order offline and checks rendered cover pixels with zero further server requests.
